A living atlas of biodiversity

LinNeo

A knowledge graph with ~2.5 million species from GBIF, enriched from multiple sources and navigable like the tree of life. Built as the documentary foundation for a book's worldbuilding.

§ Overview

What LinNeo is

LinNeo takes the GBIF taxonomic backbone and models it as a graph in Neo4j: each taxon is a node and the hierarchy is expressed through HAS_CHILD relationships, from a root node Biota down to each species. Enriched information from several sources hangs off that skeleton —descriptions, common names, images, sounds, geographic distribution, and conservation status— so every species can be queried as a full record.

It's consumed through an API (FastAPI) and a web interface (React) with three visual themes. The ultimate purpose isn't academic but creative: to serve as a reference atlas for building a book's natural world, letting you explore kinship, distribution, and traits of real organisms.

~2.5M species

Full GBIF backbone coverage, all kingdoms.

9 kingdoms · 4 domains

Hierarchy crowned by Biota → Domain → Kingdom.

Multi-source

GBIF, Wikipedia, EOL, FishBase, POWO, AmphibiaWeb, Wikidata, Wikimedia, Xeno-canto.

3 themes

elixir, bookworm, and shui (oceanic, the home page).

Why ln_ss10 leaves the per-kingdom count visible

The infographic deliberately keeps the species-by-kingdom breakdown visible (instead of hiding or normalizing it) because it works as a visual diagnostic for data cross-checks: if thousands of species show up whose declared kingdom doesn't match the kingdom they're structurally reachable from, that's exactly the kingdom-misplacement issue described in Integrity & repair — visible at a glance instead of hidden inside a query.

Unresolved performance

Taking these screenshots made a real limitation obvious: detail-heavy views take a few seconds to load, even when capped at a maximum of 250 species per query. Fetching that much data efficiently still hasn't been solved. Even so, navigability and the interactive exploration of the tree of life —graphs you can focus node by node, maps, galleries, and live sound trees— is one of the project's biggest strengths.

§ Architecture

Architecture

Three layers running in parallel:

LayerTechnologyRolePort
DatabaseNeo4j (database linneo)Taxonomic graph + enrichment. Auth disabled locally.7687 / 7474
BackendFastAPI (uvicorn)Translates HTTP requests into Cypher and returns JSON.8035
FrontendReact + ViteUI; /api proxy → localhost:8035.5135

The runtime flow is linear: the browser calls /api/*, Vite forwards it to the backend, FastAPI runs the Cypher query against Neo4j, and returns JSON that the frontend renders (species pages, graphs, maps). Besides runtime, there's an offline data pipeline (Python scripts + Cypher loaders) that populates the database once; see Pipeline.

Golden rule

uvicorn's --reload only reloads the backend; Vite's HMR reloads the frontend on save. Every change to package.json requires npm install. Never use npm audit fix --force.

§ Data model

Data model in Neo4j

The graph is structured on two planes: the taxonomic hierarchy (a single HAS_CHILD chain from Biota down to each species) and the enrichment hanging off species (descriptions, media, distribution).

Upper hierarchy

The top is set by setup_biota_domains.cypher (in the repo, domain_key.cql), idempotent and self-correcting:

DomainkeyKingdoms
Eukaryota1Animalia, Plantae, Fungi, Chromista, Protozoa
Prokaryota2Bacteria, Archaea
Viruses3Viruses
incertae sedis4incertae sedis

Prokaryota isn't a formal domain in the three-domain system (Bacteria and Archaea are usually separate), but it was deliberately chosen this way for the project's hierarchy.

Critical gotcha · key scheme

Keys are not uniform across ranks. family, genus, and species use the GBIF taxonID as their key (e.g. Amanitaceae=23780, Amanita=257861). kingdom, phylum, class, order, and domain, on the other hand, use small in-house numbering (e.g. Basidiomycota=16, Agaricales=50). Any cross-reference with GBIF data must respect this: by key at the low ranks, by name at the high ones.

Color by kingdom

The frontend tints the entire UI according to the active kingdom (kingdomColor.js, KINGDOM_HUE map):

Animalia 48° Plantae 135° Fungi 280° Chromista 172° Bacteria 212° Archaea 28° Protozoa 328° Viruses 2° incertae sedis
§ Data pipeline

Data pipeline

Populating the database is a four-stage offline process. Outputs live in biodiversity_data/.

1 · Download and sources

pipeline/download_all.py orchestrates the fetchers, and pipeline/fetchers/download_biodiversity_data.py downloads the GBIF backbone (backbone.zip), from which taxonomy, distribution (242 countries), and conservation are extracted. Each fetcher adds an enrichment layer:

FetcherContributesOutput
wikipedia_fetcherDescriptionsdescriptions/wikipedia_descriptions.csv
eol_fetcherDescriptions (Encyclopedia of Life)descriptions/eol_descriptions.csv
fishbase_fetcherFish datafishbase/fishbase_fish.csv, species.parquet
powo_fetcherPlants (Plants of the World Online)powo/powo_plants.csv
amphibiaweb_fetcherAmphibiansamphibiaweb/amphibiaweb_data.csv
wikidata_fetcherCommon nameswikidata/wikidata_common_names.csv
wikimedia_images_fetcherImagesimages/wikimedia_images.csv
xeno_canto_fetcherBird soundsxeno_canto/xeno_canto_sounds.csv

Each fetcher keeps its own *_progress and *_fetcher.log to resume and audit.

2 · Backbone extras

pipeline/backbone_extras.py processes the backbone extract (not included in this documentation) and generates backbone_csv/: descriptions (all languages, cleaned HTML), vernacular_es (common names), images, references, and type specimens. Approximate coverage: 1.08M references, 551K descriptions, 224K vernaculars, 192K multimedia, 35K types.

3 · Cleanup

pipeline/clean4neo4j.py normalizes the CSVs so LOAD CSV can ingest them without errors.

4 · Load

The loaders in pipeline/loaders/ import each layer into Neo4j (one per source):

cypher_import_taxonomy.cypher       # nodes per rank + hierarchy
cypher_import_relationships.cypher  # FOUND_IN, PART_OF (geography)
cypher_import_backbone.cypher       # descriptions/media/refs from the backbone
cypher_import_wikipedia.cql         cypher_import_powo.cql
cypher_import_wikidata.cql          cypher_import_fishbase.cql
cypher_import_amphibiaweb.cql       cypher_import_images.cql
cypher_import_sounds.cql

Final nodes per rank live in taxonomy_nodes_by_rank/, and relationships per level in relationships/.

§ Integrity & repair

Integrity maintenance 89% resolved

Methodology, in short

For every variant of the problem (orphans, multi-parent, misplaced) the same pattern was followed: 1) diagnose with Cypher how many nodes and of what type, never repair blindly; 2) cross-reference the backbone (Taxon.tsv) by taxonID, and if the key isn't there, fall back to name+rank with a uniqueness safeguard to avoid grabbing homonyms from another kingdom; 3) walk up the parentNameUsageID chain, skipping unmodeled ranks, until the first real ancestor; 4) generate CSV + idempotent Cypher instead of editing the graph by hand, so it can be re-run, audited, and reverted. Genuinely ambiguous cases are deliberately left untouched.

The original load left the graph with two big wounds that were diagnosed and repaired in depth.

Problem 1 · Missing Fungi kingdom

171,665 species had kingdom='Fungi', but no Kingdom node for Fungi existed, nor its upper links: 7,945 families and 11 phyla ended up orphaned. Cause: in GBIF, many Fungi taxa hang directly off the Kingdom (taxonID 5), and since that node was never created during the load, they were left loose.

Problem 2 · 26,747 orphan nodes

An audit revealed the problem wasn't exclusive to Fungi: there were nodes with no HAS_CHILD parent across all ranks (19,608 genera, 6,795 families, 171 species, 158 orders, 15 classes). Every loose intermediate node disconnects its entire branch from the tree.

Diagnosis

  • Mixed key scheme (see Data model): prevented cross-referencing uniformly by ID.
  • Unmodeled intermediate GBIF ranks (subfamily, tribe, subgenus): many genera hang off a subfamily, not a family directly.
  • Nodes from other sources: ~18,800 genera/families with in-house numbering keys (1…266,446) that don't exist as a taxonID in the backbone — fossils, real taxa, and environmental sequences (UNITE Species Hypotheses, unranked rank).

Solution

The repair_orphans.py script rebuilds the links following this strategy:

  • Reads the graph's orphan export + the backbone's Taxon.tsv.
  • Identifies the orphan by its graph key (exact match within the graph).
  • Walks up the parentNameUsageID chain, skipping unmodeled ranks, until the first main ancestor.
  • Name fallback: if the key isn't in the backbone, searches by name+rank (with a uniqueness safeguard to avoid grabbing homonyms from other kingdoms).
  • Generates orphan_links.csv plus a custom-built repair_orphans.cypher (one block per child→parent combination, choosing a match by key or by name).

Result: 23,867 of 26,747 reconnected (89%). ~1,346 remain, mostly ambiguous homonyms (where the safeguard deliberately abstained) and UNITE environmental sequences — noise irrelevant to the project.

Problem 3 · Nodes with multiple parents across kingdoms

Reconnecting orphans revealed another wound: nodes with more than one incoming HAS_CHILD relationship, some crossing different kingdoms — duplication from divergent backbone paths. dedupe_by_kingdom.cql applied the same methodology (above), filtering by the real kingdom deduced from descendant species: genus went from 3,525 down to 1,205 multi-parent nodes, family from several down to 7. What's left is multi-parent within the same kingdom (genuine sibling nodes, e.g. taxonomic synonyms) — harmless since they don't cause cross-kingdom leaks, so they're left as optional low-priority polish.

Taxon.tsv has huge fields; every script that reads it raises the csv module's limit with csv.field_size_limit(...). Name/key cross-references require Neo4j indexes (created by repair_orphans.cypher itself).

§ Capabilities & limits

Capabilities and limitations

What it can do

  • Navigate the tree of life from Biota to ~2.5M species with interactive graphs, focusable node by node.
  • Show species pages: taxonomy, distribution (242 countries), conservation (IUCN), multi-source and multilingual descriptions, images, sounds, and common names.
  • Search by name and within descriptions; filter by geography (continent → country).
  • Tint the entire UI by kingdom and switch between three themes.

Navigability and interactive exploration are, right now, the project's biggest strength: maps, galleries, and live sound trees, not just data tables.

What it can't do (yet)

  • Unresolved loading performance: detail-heavy views take a few seconds even when capped at 250 species per query.
  • ~1,346 orphan nodes (marginal taxa and environmental sequences) remain outside the tree.
  • ~33,300 species with kingdom misplacement (diagnosed, fix designed, execution pending).
  • Enrichment is partial: not every species has an image, sound, or description.
  • The data is a snapshot; updating it requires re-running the pipeline.
§ Known gotchas

Known gotchas

Key scheme

family/genus/species = GBIF taxonID; kingdom/phylum/class/order/domain = in-house numbering. Don't assume uniformity when cross-referencing data.

Neo4j Browser export

Truncates to ~5,000 rows by default. For large dumps use cypher-shell --format plain > file.csv or raise "Maximum number of records".

UNITE / unranked

The Fungi backbone includes hundreds of thousands of Species Hypotheses (codes like SH1129775.09FU, unranked rank) hanging off the Kingdom. They're noise and don't connect as named taxa.

Homonyms across kingdoms

The same genus name can exist in several kingdoms. Name-based cross-references carry a uniqueness safeguard; ambiguous ones are deliberately left untouched.

§ Project challenges

Project challenges

The biggest problems faced throughout development, how they were diagnosed, and where they stand. The general methodology is under Integrity & repair; here's the record of each specific challenge.

Entire Fungi kingdom disconnected resolved

171,665 species had kingdom='Fungi', but no Kingdom node for Fungi existed: 7,945 families and 11 phyla ended up orphaned. The real challenge was identifying which nodes belonged to Fungi without having the kingdom property on hand at the intermediate ranks. Solution: start from the Fungi species (which do carry the property), walk up the existing HAS_CHILD relationships as far as they'd go, identify where the chain broke, and rebuild from there using Taxon.tsv to create the Kingdom and the missing links.

~26,747 orphan nodes across all ranks 89% resolved

Generalizing from the Fungi problem, the same pattern of parentless nodes turned up in genera, families, species, orders, and classes across all kingdoms. repair_orphans.py resolved 23,867 of 26,747 (89%) by cross-referencing taxonID or, failing that, name+rank with a uniqueness safeguard.

Nodes with multiple parents across kingdoms ~99% resolved

dedupe_by_kingdom.cql brought genera with multiple parents down from 3,525 to 1,205 and families to 7. A second pass, dedupe_parents.py (v3→v4, five resolution steps: direct key match, name+kingdom+lineage, fusion of duplicates with a common ancestor, real kingdom of descendant species as a tiebreaker, and a single verifiable parent by elimination), resolved 3,510 of 3,532 cases (99.2%), leaving 10 genuinely ambiguous and 2 node fusions. Side effect detected: 38 genera ended up orphaned because their "kept" parent was never a real edge in the graph — they were reclassified as standard orphans and repaired with repair_orphans.py v2 (which also added the kingdom filter to its name fallback, resolving 339 additional previously-ambiguous cases).

Kingdom misplacement diagnosed, execution pending

~33,300 species are reachable from a different kingdom than the one declared in their kingdom property (e.g. plants hanging under Animalia). Confirmed diagnosis: this isn't duplication but a single wrong parent per node (1,927 cases with one parent, 21 with two, 1 with three, just for plant genera trapped under Animalia). The designed solution reuses the repair_orphans/dedupe_parents machinery: resolve the true parent in the backbone filtered by the real kingdom (deduced from descendant species), then MERGE the correct edge + DELETE the wrong one. It's visible in the frontend's per-kingdom infographics (see Screenshots).

MemoryPoolOutOfMemoryError on the infographic resolved

Requesting the infographic for a full kingdom (/taxon/kingdom/{key}/infographic) could materialize potentially millions of species across all its phyla in a single transaction before the limit could be applied, exceeding the configured heap. Fixed by moving the filter and the LIMIT into a CALL (ph) { ... } subquery per phylum, so Neo4j processes each one as its own bounded unit instead of accumulating the whole kingdom's universe.

Graph coloring didn't inherit by kingdom at depth resolved

Descendants of a kingdom were supposed to inherit its color at any depth, but it got lost at intermediate nodes. Fixed with a backend fallback that walks up HAS_CHILD* until it finds the real Kingdom ancestor.

Graph focus saturated for large kingdoms resolved

A direct consequence of reconnecting orphans: graph_focus could return thousands of children (Fungi especially) and saturate the radial layout. Capped at 60 children on the first level and 15 per sibling on the second, prioritized by descendant count.

Race condition in the search/graph resolved

In Shui.jsx, a late-resolving graphFocus promise could overwrite a later graph reset. Fixed with a counter (focusOpRef) that discards results from stale operations.

Loading performance with detail-heavy views unresolved

Information-dense views take a few seconds to load even when capped at a maximum of 250 species per query. Fetching that much data efficiently still hasn't been optimized — it's the project's most visible limitation today, though navigability and interactivity remain among its biggest strengths.

§ Roadmap

Roadmap

  1. Execute the kingdom-misplacement fix pending — ~33,300 species; solution already designed (see Project challenges).
  2. Loading performance with detail-heavy views pending — still no efficient way to fetch that much data at once.
  3. Domain rank in the frontend pending — add Domain to colors/labels and decide whether ShuiGraph should start at Biota → Domain → Kingdom.
  4. shui polish pending — have the example bar respect active kingdoms; smooth transitions between themes.
  5. More bookworm views pending — new clade "toys".
  6. Deployment pending — GitHub Pages for the frontend; backend + Neo4j hosted.
  7. Genomic layer future — add DNA, chromosome, and sequence information as an extra enrichment layer on top of existing species.
  8. GBIF Ebbe Nielsen Challenge future — consider submitting LinNeo once it's deployed and the genomic layer is added.

Completed in the frontend session: search autocomplete (keyboard navigation, highlighting, rank/kingdom context, states), the graph cap in queries.py, and the three new bookworm views (gallery, sound tree, infographic).

Closing the ~1,346 remaining orphans (disambiguating homonyms by the kingdom of descendant species) is optional and low-value for the project's goal.
